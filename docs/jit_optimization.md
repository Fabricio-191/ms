# JIT Optimization Status

Analysis of how V8 compiles the functions in this library, measured with `%GetOptimizationStatus` on Node.js v24.11.1 (V8 13.x) after 100,000 warmup calls per function.

## Running the benchmark

```bash
npm run bench:jit
# Or directly:
node --allow-natives-syntax --import tsx/esm testing/benchmarks/jit.ts
```

## What is being measured

The benchmark inspects the **functions returned by `buildParse` and `buildFormat`** — these are generated at runtime via `new Function()` and represent the actual hot path that parses/formats your data.

## Results

| Function | V8 Status | Raw | Tier | ops/sec |
|---|---|---|---|---:|
| `buildParse` (v42) | Optimized + Interpreted | 81 | Maglev | ~3,199 |
| `buildFormat` (v16, short l=1) | Optimized + TurboFan | 49 | TurboFan | ~3,750 |
| `buildFormat` (v16, long l=1) | Optimized + TurboFan | 49 | TurboFan | ~3,605 |
| `buildFormat` (v16, short l=3) | Optimized + TurboFan | 49 | TurboFan | ~1,707 |
| `buildFormat` (v16, long l=3) | Optimized + TurboFan | 49 | TurboFan | ~1,287 |

## Status bitmasks

| Bit | Value | Meaning |
|---|---|---|
| `kOptimized` | 16 | Compiled by an optimizing JIT |
| `kTurboFanned` | 32 | Specifically compiled by TurboFan |
| `kInterpreted` | 64 | Still has interpreter bytecode (Maglev coexists with it) |

- Status `81` (16 + 64 + 1) = **Maglev** with bytecode backup
- Status `49` (16 + 32 + 1) = **TurboFan** (full optimization)

## Why `buildParse` stays at Maglev

The generated parse function has:
- **Large body** (~150+ lines of generated code with flat if-chains)
- **Complex control flow** (trie dispatch with many branches)
- **High cyclomatic complexity** from notation matching

V8's TurboFan heuristics reject functions with this profile — the compilation cost outweighs the expected benefit. Maglev is already highly optimized and achieves ~213K ops/sec.

## Why `buildFormat` reaches TurboFan

The generated format function has:
- **Small, predictable body** (early-return chain or simple accumulation)
- **Linear control flow** (no complex branching)
- **Low complexity** (just arithmetic and string concatenation)

This matches TurboFan's criteria for "simple hot functions worth fully compiling."

## Key insight

The JIT tier depends on the **generated function's body complexity**, not the creation method. Both `buildParse` and `buildFormat` use `new Function()` — what matters is what code gets generated inside.

| Factor | `buildParse` | `buildFormat` |
|---|---|---|
| Creation | `new Function()` | `new Function()` |
| Body size | Large (~150+ lines) | Small (~20-40 lines) |
| Branch complexity | High (trie dispatch) | Low (linear chain) |
| JIT tier | Maglev | TurboFan |
| Performance | ~213K ops/sec | ~3,600 ops/sec |

> Note: `buildFormat` is slower in absolute terms because formatting does more work (string operations), but it reaches a higher JIT tier because the code pattern is simpler.

## Historical context

Earlier versions of this library used `.bind()` to pre-close arrays, creating a `JSBoundFunction` that couldn't be inspected with `%GetOptimizationStatus`. The current implementation (v42/v16) returns plain functions generated by `craftFunction`, which are directly inspectable.

## Limitations of `%GetOptimizationStatus`

- Requires `--allow-natives-syntax` flag
- Status values are V8 internals and may change between versions
- Only works on `JSFunction` objects (not bound functions, proxies, etc.)
